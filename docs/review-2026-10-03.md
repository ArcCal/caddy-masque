# Pre-production audit — caddy-masque (2026-10-03)

Baseline: `078cdfb` (main). This is the Go/Caddy companion to the lead
report in [ArcCal/masque-vpn `docs/review-2026-10-03.md`](https://github.com/ArcCal/masque-vpn/blob/main/docs/review-2026-10-03.md),
which covers the Rust core and the Mac app and holds the overall verdict,
the IETF-conformance table and the go-live checklist. This pass **audits
only and changes no code.**

> **Status, later the same day:** all six findings are fixed: C1, C3 and C4
> in ArcCal/caddy-masque#17, and C2, C5 and C6 in the pull request after it
> (see the "Fixed" line under each). Verified with `go test -race ./...`,
> `go vet` (also for macOS) and gofmt, and `tests/e2e-netns.sh`: 212 passed,
> 0 failed, 11 skipped (the IPv6 checks; this kernel has IPv6 off). Among the
> passes are four new checks of the admin socket and three of an HTTP/2
> client that vanishes. The e2e suite now runs Caddy with its admin API on a
> socket, as the service does, and with the site line the installer writes,
> so every tunnel it opens names the server by IP address. The rest of this
> document describes the code as it was before those fixes.

Goals: as close to the IETF standards as possible, secure, reliable, easy to
use.

## How this was checked

- Read every `.go` file line by line, with attention to where the port
  diverges from the Rust core that earlier passes vetted.
- Built Caddy with the module and ran the repository's own end-to-end suite
  against the real Rust `masque-client`: **205 passed, 0 failed, 11 skipped**
  (the IPv6 checks; this kernel has IPv6 off). `go test -race ./...` passes;
  `go vet` and `gofmt -l` are clean; `govulncheck` reports **0 reachable
  vulnerabilities** (1 unreachable module advisory, GO-2026-5932 in
  `x/crypto/openpgp`, which the code never calls).
- Reproduced or measured C1, C3, C4 and C6 (commands are under each).

## Verdict

The port is faithful and interoperates with the Rust client over HTTP/3,
HTTP/2 and HTTP/1.1. The protocol logic, the forwarding checks, the cover
site and the host-protection `input` chain are all correct. The findings are
the places where the Go code **did not inherit the hardening the Rust side
landed in its last two passes**, plus two deployment-shaped issues. One of
them (C1) is exploitable by any authenticated user today.

Severity: **High** = fix before production; **Medium** = fix before
production or have the mitigation in place; **Low** = later.

## High

### C1. ROUTE_ADVERTISEMENT validation is quadratic — 260 ms of CPU per 64 KB, measured

- **Where:** `internal/proto/capsule.go`, `ValidateRoutes` — the
  protocol-0-overlap check is a nested loop over every pair of ranges.
  `Decode` calls it for **every** ROUTE_ADVERTISEMENT capsule
  (`capsule.go`, the `TypeRouteAdvertisement` case), which runs on the
  server for capsules a client sends even though the server then ignores
  client routes (`session.go`, `readCapsules`, the `default` arm).
- **Measured, this environment** (release-ish `go test`, one 2.1 GHz core):
  a 65 540-byte capsule holding 6 554 ranges (3 277 protocol-0 then 3 277
  protocol-6, disjoint and sorted, so the ordering check passes and the
  overlap loop runs in full) takes **259 ms** per `Decode`. The linear parts
  are sub-millisecond; the overlap loop is the whole cost.
- **Consequence:** an authenticated client (or a malicious peer, if the
  module is ever a client) streams these capsules back-to-back. At ~190
  capsules/s — a few Mbit/s of upload — that is ~45 CPU-seconds per
  wall-second, i.e. it saturates every core. Each `Decode` also blocks the
  goroutine for a quarter second, stalling other connections scheduled on
  that thread. A single account takes the server down.
- **This is the Rust side's N4, already fixed there.** Port the same
  algorithm: the ranges are already checked to be sorted by (version,
  protocol, start); within each version the protocol-0 ranges come first and
  are disjoint, so binary-search each protocol-specific range against them
  (`O(n·log n)`). The Rust `masque_proto::connect_ip::validate_routes` is the
  reference. RFC 9484 §4.7.3 makes this check OPTIONAL, so the server — which
  ignores client routes — could alternatively skip it on inbound capsules
  entirely. Add a regression test that validates a 6 554-range capsule within
  a time bound.
- **Reproduce:** a throwaway test in `internal/proto` that builds the capsule
  above and times `Decode` (the audit used exactly this; it printed
  `Decode: 259.510736ms per capsule`).
- **Fixed:** `ValidateRoutes` now uses the Rust algorithm: the ordering
  check stays linear, and each protocol-specific range is binary-searched
  against the protocol-0 ranges of its IP version. Decoding the capsule above
  takes about 1.2 ms (about 215 times faster); the remaining time is decoding
  6 554 ranges. New tests: `TestProtocolZeroOverlapIsFoundWhereverItIs` (the
  Rust cases: overlaps at either end, a range covering a protocol-0 one,
  adjacency, a range between two protocol-0 ones, IP versions) and
  `TestAFullRouteCapsuleIsCheckedQuickly`, which fails on the old code (1.8 s
  for 10 capsules against a 1 s bound) and checks that an overlap in the
  middle of a full capsule is still found.

## Medium

### C2. A password-verification flood can still delay legitimate reconnects

- **Where:** `internal/auth/auth.go` (`Authenticator.Verify`, `slots` =
  2×CPU, `waiting` bounded at `slots × 32`, then `ErrBusy` → 503) and
  `internal/auth/throttle.go` (`FailureLimiter`: after 10 wrong credentials
  in a minute from one address, its credentialed requests are treated as
  anonymous for a minute).
- **What's missing vs. the Rust server (N2):** there is **no per-source cap
  on verifications in flight** and **no cache of recently verified
  credentials**. The failure-limiter only engages *after* failures are
  recorded, i.e. after the slow Argon2 verifications complete — so an opening
  burst from one source, or a distributed flood from many sources each
  staying under 10 failures/minute, can fill the 2×CPU Argon2 slots and the
  queue, and every request that arrives meanwhile — a legitimate reconnect
  included — gets 503 until the flood eases. Generated passwords are 144-bit
  and unguessable, so this is availability, not credential theft.
- **Fix:** mirror the Rust server's two additions:
  - cap verifications in flight per source address (IPv4 /32, IPv6 /64) at a
    small number (the Rust side uses 4), so one source cannot fill the queue;
  - cache successful verifications in memory, keyed by an HMAC (random
    per-process key) of name‖0‖password, valid for a few minutes and only
    while the user's configured hash is unchanged, so a returning user skips
    Argon2 and the queue entirely. Only correct passwords enter the cache, so
    a flood cannot fill it.
- **Fixed:** as in the Rust server. `Authenticator.Verify` takes the
  client's address and lets one source (an IPv4 address or an IPv6 /64) have
  at most 4 verifications waiting or running, with 503 beyond that; a
  cancelled request gives its place back, unless the hashing it started is
  still running. Credentials verified in the last 12 hours are remembered
  (HMAC-SHA256 of name‖0‖password under a random key made at start-up),
  only while the user's hash is unchanged; each use renews the entry, and
  expired entries are dropped when one is added. `handler.go` checks
  them first, so a remembered user skips Argon2, the queue, the per-source
  cap and the failure limiter. This also means a user behind a shared address
  is not locked out by someone else's wrong passwords. New tests:
  `TestRememberedCredentialsGetInWhileAFloodFillsTheQueue`,
  `TestAChangedOrRemovedPasswordIsNotRemembered`,
  `TestRememberedCredentialsExpire`, `TestOneSourceCannotFillTheQueue`,
  `TestACancelledVerificationKeepsItsPlacesUntilHashingFinishes`,
  `TestSourcesAreAddressesOrIPv6Slash64s`, and in the Caddy harness
  `TestCaddyRememberedLoginSkipsTheThrottle`.

### C3. The Caddy admin API is open to other local users, under the root service

- **Where:** the module never configures Caddy's admin endpoint;
  `deploy/install-server.sh` and `deploy/Caddyfile.example` do not either, so
  it is Caddy's default: `localhost:2019`, **no authentication**. The service
  runs as root.
- **Reproduced, this environment:** with the server running, an unprivileged
  local user read the configured users and their Argon2 hashes:

  ```
  $ runuser -u nobody -- curl -s localhost:2019/config/apps/masque/users
  [{"name":"laptop","password_hash":"$argon2id$v=19$m=19456,t=2,p=1$…"}]
  ```

  The same endpoint accepts `POST /load` and `POST /stop`: any local process
  can reconfigure or stop the VPN, or read its whole config.
- **Consequence:** on a single-tenant VPS this is low (only root-equivalent
  users are around). On any host with other user accounts or other service
  users it is a privilege/parameter-disclosure and a local denial of service.
  The README's note that the admin endpoint "listens only on localhost…out
  of the clients' reach" addresses *VPN clients*, not *other local users*.
- **Fix:** bind the admin endpoint to a unix socket with `0600`
  (`admin unix//run/caddy-admin.sock`) or turn it off (`admin off`) in the
  Caddyfile the installer writes; mention it in the README's "Protecting the
  server itself" section. If the admin API is wanted, restrict it and keep
  it off `0.0.0.0`.
- **Fixed:** `deploy/caddy-masque.service` sets
  `CADDY_ADMIN=unix//run/caddy-masque/admin.sock|0600` (Caddy's default admin
  address, which `caddy reload` falls back to as well), with
  `RuntimeDirectory=caddy-masque` (mode 0700) for the socket. Doing this in
  the unit rather than in the Caddyfile also covers existing installations,
  whose Caddyfile `install-server.sh` keeps but whose unit it replaces; the
  installer warns when an existing Caddyfile sets `admin` itself. The README
  (protecting the server, monitoring) and the installer's closing hints show
  the socket. Checked in a namespace with the server running: socket mode
  0600, nothing on TCP 2019, root reads `/metrics` through the socket,
  `nobody` is refused (even with the directories above it opened for
  traversal), `caddy reload` works through `CADDY_ADMIN` and through
  `--address`. The e2e suite now runs Caddy this way, so all its reloads go
  through the socket, and it checks the mode, the closed port, root's access
  and `nobody`'s refusal.

### C4. The Mac app's optional "IP" field breaks against a default-installed server

- **Where:** the virtual-host routing is Caddy's: a request is matched to a
  site block by its `Host` / `:authority`. `install-server.sh` writes a
  Caddyfile whose only site address is the domain (`$DOMAIN { … masque … }`).
  The Mac app's "IP (optional)" field, and masque-vpn's `uri_template` with
  an IP authority plus `server_name`, make the request's authority the **IP
  literal** while TLS SNI stays the domain.
- **Reproduced, this environment** (Caddyfile with a single `vpn.test` site,
  as the installer writes; client with `uri_template` authority = the
  server's IP, `server_name = vpn.test`):

  | authority | HTTP/2 | HTTP/3 | HTTP/1.1 |
  |---|---|---|---|
  | IP literal | `session failed: response (200 OK) is malformed: it has content` | same | `server did not accept the CONNECT-IP request (200 OK)` |
  | domain | `tunnel up` | `tunnel up` | `tunnel up` |

  The IP-authority request matches no site block, falls to Caddy's default
  empty response (a 200/404 with a body), and the client rejects it as
  malformed — with an error that gives the user no hint that the IP field is
  the cause. The Rust `masque-server` is **not** affected: it routes
  CONNECT-IP by the URI-template path regardless of authority, so the IP
  field works there (that is what the Mac app's README describes, and it is
  true only for the Rust server).
- **Fix (pick one):** have `install-server.sh` write the site line as
  `$DOMAIN, https://$PUBLIC_IP {` (one block, one cert, both authorities —
  the end-to-end suite already proves this works because it lists
  `https://vpn.test, https://$SERVER`); **or** document in both READMEs that
  the Mac app's IP field is for the Rust server and that caddy-masque needs
  the IP added as a site address; **or** have the handler, when a CONNECT-IP
  request's path matches the template but no site matched by authority, still
  serve it. The first is the smallest change and matches what the tests
  already cover.
- **Fixed, differently:** listing the IP as a site address turned out to be
  the wrong fix: certmagic counts a public IP address as eligible for a
  public certificate, so Caddy would also try to get one from the public CAs
  for it. `install-server.sh` and `deploy/Caddyfile.example` now write
  `$DOMAIN, :443 {`. The adapted configuration keeps the domain under
  certificate automation (`tls.certificates.automate`) and gives the site a
  catch-all route, so HTTPS requests for any other host name on port 443,
  the server's IP included, reach `masque` (and the cover site); no
  certificate is requested for the catch-all, and HTTP is still redirected to
  HTTPS. Checked in a namespace with automatic HTTPS (Caddy's internal CA
  standing in for the ACME CA): with `vpn.test {` the IP-authority tunnel
  fails on all three transports as above; with `vpn.test, :443 {` both
  authorities bring the tunnel up over HTTP/3, HTTP/2 and HTTP/1.1, the cover
  site answers 200 and `http://` is redirected. For installations whose
  Caddyfile the installer keeps, it now prints the one-line change, and the
  README explains how sites are chosen by host name. The e2e suite uses the
  same site line, so its tunnels, which name the server by IP address, cover
  this path.

## Low

### C5. A dead TCP tunnel is reclaimed slowly (no TCP_USER_TIMEOUT)

- **Where:** `handler.go` clears the tunnel stream's read/write deadlines
  (`SetReadDeadline(time.Time{})`, `SetWriteDeadline(time.Time{})`) and the
  module sets no `TCP_USER_TIMEOUT`; detection of a vanished TCP peer falls
  to Caddy's OS keepalive (defaults: idle 15 s, interval 15 s, count 9 ≈
  150 s). HTTP/3 tunnels close at the 60 s QUIC `MaxIdleTimeout` (`app.go`).
- **Consequence:** when a client's network changes (a laptop or phone — the
  Mac app's whole use case), its old HTTP/2/1.1 tunnel holds its address and
  its `max_sessions` slot for ~2.5 minutes. With `max_sessions` default 8 a
  single roaming device will not normally lock itself out, but a device that
  flaps repeatedly can briefly hit 429. The Rust server sets
  `TCP_USER_TIMEOUT=30s` and reclaims within ~30 s.
- **Fix:** set `TCP_USER_TIMEOUT` (Linux) on accepted tunnel connections, or
  shorten the keepalive (`keepalive_interval`/`keepalive_count`) for the VPN
  server; document the trade-off. Low priority given the default
  `max_sessions`.
- **Fixed:** the connections that carry HTTP/1.1 and HTTP/2 tunnels get the
  Rust server's settings, whatever Caddy's keepalive options: keepalive
  probes after 10 s idle, every 5 s, 4 of them, and a `TCP_USER_TIMEOUT` of
  30 s (Linux). For HTTP/2 the handler registers Caddy's connection-context
  hook while provisioning (`RegisterConnContext`, Caddy's documented way to
  reach the connection). The TCP connection is found under TLS, the PROXY
  protocol and Caddy's listener wrappers. `TestTunnelsOverTCPGetShortTimeouts`
  reads the socket options of real tunnel connections through Caddy's
  listeners. A new check in `tests/e2e-netns.sh` cuts an HTTP/2 client off in
  the router. The server ended its session after 30 s. With a build from
  before the fix, the same check fails: the session was still up when the
  check's 45 s ran out.

### C6. An IPv6 pool between /97 and /112 reuses addresses without clearing conntrack

- **Where:** `internal/pool/pool.go`, `randomIIDBits = 16`: a family with
  `hostBits < 16` is *tracked* (reuse clears conntrack); `/112` has exactly
  16 host bits, so `/97`–`/112` use **untracked random allocation**, and
  `Allocate` returns `usedBefore = false` even for an address a previous
  session used — so `core.go`'s `acquire` does not flush its conntrack
  entries, the very isolation C's Rust twin (M2) set out to guarantee.
- **Measured, this environment:** 2 000 sequential sessions on an `fd00::1/112`
  pool handed a previously-used address with `usedBefore=false` **21–30
  times** (≈1–1.5 %); on those, replies for the old session's connections can
  reach the new session.
- **Not triggered by the defaults:** `install-server.sh` and the example use
  a `/64` v6 pool (64 host bits, random IIDs that essentially never repeat),
  and the IPv4 pool is always tracked. This bites only an operator who
  configures a `/97`–`/112` v6 pool.
- **Fix:** raise `randomIIDBits` to 64 to match the Rust side (`RANDOM_IID_BITS
  = 64`), or track reused addresses for every prefix length; or reject
  `/97`–`/112` v6 pools in config validation with an explanation. Until then,
  keep the v6 pool at `/64` or wider (the default).
- **Fixed:** `randomIIDBits` is 64, as on the Rust side. Only a `/64` or
  shorter gets random interface identifiers. Smaller IPv6 pools are tracked
  like IPv4 ones, so a reused address is reported and its conntrack entries
  are cleared. (Every prefix from `/65` to `/112` was untracked before; the
  shorter ones only collided less often.)
  `TestIPv6PoolsSmallerThanA64TrackReuse` runs 70 000 sessions on a `/112`
  and checks that every reuse is reported; on the old code it fails at the
  first unreported reuse, after about 700 sessions. It also checks `/65` and
  `/96` pools.

## Checked and sound (no action)

- **Isolation:** per-packet BCP 38 source check and scope check
  (`session.go`, `clientPacket`); clients cannot reach each other or the host
  by default (the `input` chain, `internal/hostnet`); reused IPv4 addresses'
  conntrack is cleared before hand-out, and the whole pool at startup
  (`core.go`, `start`/`acquire`).
- **Cover site:** non-CONNECT-IP, wrong-path, wrong-credential and
  no-TLS requests all get the ordinary site response; CONNECT over h2/h3 gets
  the site with a non-2xx (a 2xx would mean "tunnel established"); `Alt-Svc`
  is advertised like a real HTTP/3 site. Reproduced against the real client.
- **MTU probe (§7.2):** the server actively sends the 1280-byte ICMPv6 echo
  probe and tears the tunnel down without a whole, checksum-valid reply
  (`session.go`, `probeMTU`/`isProbeReply`) — stricter than masque-vpn, and
  correct. (This is why the Mac app's bundled client needs the ping-answer
  fix, which it has.)
- **Fragment scoping (§4.8):** later IPv6 fragments are scoped by the first
  fragment's upper-layer protocol, bounded to 64 remembered fragments for a
  fragment lifetime (`session.go`, `fragments`).
- **Reloads:** removed/changed users disconnected at once; widened scopes
  re-advertised, narrowed scopes end the affected tunnels; failed reload
  rolls back (`core.go`, `app.go`).
- **Injection:** external commands run via argv, never a shell
  (`internal/hostnet`); nftables loaded atomically; interface names,
  user names and prefixes validated.
- **systemd unit:** `deploy/caddy-masque.service` is well hardened and is the
  model the masque-vpn units should copy.
- **Supply chain:** `govulncheck` in CI (push, PR, weekly); Dependabot;
  build-provenance attestations on release archives. Good. (Actions are
  pinned by tag, not SHA — a minor supply-chain hardening, same note as the
  Rust side.)

## Reproduction notes

All reproductions ran as root in network namespaces in this environment
(`aud-s`/`aud-c`/`aud-c2`, a P-256 test CA, Caddy built from `./cmd/caddy`,
the Rust `masque-client` from `../masque-vpn`):

- **C1:** a `go test` in `internal/proto` building the 6 554-range,
  65 540-byte capsule and timing `Decode` → 259.5 ms per call.
- **C3:** `runuser -u nobody -- curl -s localhost:2019/config/apps/masque/users`
  with the server running → the users and their hashes.
- **C4:** client configs with `uri_template` authority = the server IP vs the
  domain, against a single-`vpn.test`-site Caddyfile, over all three
  transports → the table above.
- **C6:** a `go test` in `internal/pool` running 2 000 allocate/release
  cycles on an `fd00::1/112` pool and counting `usedBefore=false` hits on
  already-seen addresses → 21–30 per run.
