# Comprehensive standards and interoperability recheck — 18 October 2026

## Assessment and baseline

This review re-examines the current server against the original IETF specifications, applicable verified errata and independently maintained implementations. Mandatory IETF behavior takes precedence over camouflage and other design goals. A finding requires a concrete implementation path and evidence of the relevant requirement; similarity to another implementation, a stricter test preference or a previous audit statement is insufficient by itself.

The reviewed baseline is merged main commit `27c75d5e828339d95c3ccda9a763eb6e05fe0a2a`, whose tree equals local implementation commit `5ab98ab1c38bf251f11c7571ff2bd4f29dc2d2be`. That baseline already includes the previous conformance repairs and skeptical [IETF reassessment](ietf-reassessment-2026-10-18.md). This cycle looks beyond those earlier six implementation-file corrections; their test results are historical evidence, not fresh results for this change.

Confirmed additional problems were found in HTTP/2 SETTINGS acknowledgment, ordinary-request length enforcement, receive-window accounting and supported priority updates; HTTP/2 and HTTP/3 protocol-switch responses; HTTP/3 outgoing fields, response metadata and status parsing; QPACK field-section Base decoding; QUIC idle-timeout, receipt accounting, path validation, migration and queued-route handling; and ICMPv6 error suppression. Repairs are limited to the affected protocol paths, with baseline reproductions and valid controls. The coupled QUIC migration work requires more state and code than the small field/timeout predicates; its necessity and risk are described explicitly below. No client source, protocol dialect, dependency version, authentication scheme or build default is changed.

The completed local validation covers both supported Go toolchains, full relevant package/race suites, actual UDP QUIC v1/v2 path controls and the unchanged-client acceptance matrix. Two inherited test fixtures required corrections during that validation; their original failures and complete affected reruns are retained below. The final production footprint is 17 Go files (+886/−126); tests, exact fork records and English reports account for the remaining change. Exact source identity and publication disposition are recorded in the validation ledger. These results establish the tested behavior, with explicit native/kernel and load boundaries; they are not a formal certificate of every RFC requirement.

## Coverage and method

The review covered the complete first-party Capsule, URI-template, scope, route, address-pool, session, core, tunnel, IP-packet and host-network implementations. It also reviewed the app's provisioning and HTTP/3 takeover, request admission/refusal/acceptance, configuration parsing, credentials and throttling, reload ownership and rollback, shutdown, response/body unwrapping, TCP settings, metrics, build/install scripts and validation workflows. Documentation and design claims were checked against those paths.

Transport review examined the pinned x/net HTTP/2 server, receive/send framing, SETTINGS/flow-control/priority paths, request construction and body termination; quic-go HTTP/3 headers, request/response stream handling, control streams, QPACK, Datagrams, GOAWAY and output; and QUIC packet, parameter, handshake, address-validation, congestion/PMTU and connection-timer paths. Tests and earlier fork records were read alongside the implementations. This does not claim that every line of every transitive dependency has been audited, or that reading code proves all possible runtime configurations safe.

The normative references are RFC 9110, RFC 9113, RFC 9114, RFC 8441, RFC 9220, RFC 9218, RFC 9297, RFC 9484, RFC 9000, RFC 9001, RFC 9002, RFC 9221 and RFC 9204, with relevant URI and router requirements from RFC 3986, RFC 6570, RFC 1812, RFC 4443, RFC 8200 and RFC 6946. The review retains the distinction between verified errata and unverified reported proposals. In particular, verified RFC 9484 erratum 8444 requires `%2A` for wildcard variable expansion; the original raw-star examples are not permission for a sender to omit encoding.

Each implementation comparison is pinned to a full revision. Other projects provide independent corroboration and useful counterexamples, not a vote that overrides explicit normative text. Before/after tests isolate individual failures where possible; whole suites, race tests, valid traffic and unrelated-stream controls check the repair's boundaries. Resource limits are not removed merely to accept an artificial unbounded input.

## Confirmed findings and targeted repairs

### R1. HTTP/2 could collapse several SETTINGS acknowledgments into one

**Observed behavior.** The server represented pending SETTINGS acknowledgments with a Boolean. If several valid non-ACK SETTINGS frames arrived while the writer was blocked, they could all set the same flag and only one ACK would be written. An ACK is a synchronization point for one received frame; processing the last values is not a substitute for acknowledging each frame.

**Requirement.** [RFC 9113 §6.5.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.3) requires settings to be applied as soon as possible and an immediate acknowledgment after processing all values. Acknowledgments correspond to received frames in order. The requirement applies even when multiple frames are received before the first ACK can be sent.

**Minimum repair.** Replace the flag with a pending count in `third_party/xnet/http2/server.go`. Increment once after each valid received SETTINGS frame and consume one count for each ACK. Retain the ACK's previous scheduling priority. Charge pending ACKs against the existing control-frame budget, rather than creating an unlimited pending-control queue. All affected fields remain owned by the serve loop, and pending HPACK table changes still take effect at the existing writer boundary.

**Tests and controls.** A held-write regression receives multiple SETTINGS frames before releasing the writer and requires distinct ACKs. The budget case checks that a blocked peer cannot accumulate unlimited acknowledgments. Existing SETTINGS/HPACK table synchronization and ordinary request tests remain applicable. The earlier test that expected one ACK after two frames is corrected to expect both; it is not a reason to weaken the new assertion.

**Scope.** This repairs an actual required acknowledgment omission. It does not remove the inherited repeated-setting abuse policy: RFC 9113 §10.5 permits protective limits, so the separate duplicate-setting candidate was not established as a mandatory conformance repair.

### R2. HTTP/2 ordinary requests could end with a malformed Content-Length without a stream error

**Observed behavior.** The server could convert an invalid/unrepresentable Content-Length into zero instead of rejecting the field. For a shorter-than-declared body, ending DATA or trailers could deliver a body-reader error to the handler without performing the protocol's required stream-error action. An initial HEADERS frame with END_STREAM and a nonzero length also escaped the ordinary body-completion check.

**Requirement.** [RFC 9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6) defines Content-Length as decimal digits and requires recipients to anticipate large numerals without conversion overflow. [RFC 9113 §8.1.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.1.1) treats a content-length mismatch as malformed, with an exception for messages defined to have no content, and requires a stream error for detected malformed requests. A local `Request.Body` error alone does not complete that action.

**Minimum repair.** Validate length cardinality and conversion before creating the body pipe. Reject invalid values through the stream protocol-error path. Return the length-mismatch error from ordinary-request DATA/trailer completion, and reject nonzero initial-ended ordinary requests. A valid decimal numeral that exceeds the implementation's representable range is rejected safely; it is not described as lexically invalid solely because Go uses `int64`. Identical repeated/comma-list lengths may be rejected or normalized under RFC 9110, so rejecting them is a disclosed policy rather than an invented mandatory normalization requirement.

**CONNECT boundary.** The new ordinary-body underflow action excludes CONNECT. RFC 9110 §9.3.6 explicitly says that CONNECT requests do not have content and that subsequent data interpretation depends on the HTTP version. Its separate client rule to ignore Content-Length in a successful CONNECT response must not be misquoted as a request-side rule. An initially proposed blanket rewrite of CONNECT request length was challenged during independent review and removed. Existing generic-CONNECT behavior is preserved; Capsule Protocol's stricter prohibition on Content-Length remains a separate extension rule enforced by the MASQUE handler.

**Tests and controls.** Cases cover initial HEADERS FIN, DATA FIN and trailer FIN, invalid syntax and representational overflow, empty/exact-length/absent-length ordinary messages, continued service on another stream and preserved CONNECT cases. Independent implementations check length at these same termination boundaries: [nghttp2](https://github.com/nghttp2/nghttp2/blob/526ff38e0249acbcc4d0e8958c12cdeae9960cfe/lib/nghttp2_http.c#L597) and [hyperium/h2](https://github.com/hyperium/h2/blob/41a0f805c833666a68a293641b0979362e411b5f/src/proto/streams/recv.rs#L188).

### R3. Rejected HTTP/2 DATA could leave connection flow-control accounting inconsistent

**Observed behavior.** The receive path's combined window debit modified neither window when either the connection or stream window was too small. DATA exceeding only the stream allowance could therefore cause a stream reset without its full payload being accounted against the connection window or returning corresponding connection credit. Connection-credit exhaustion on the open, remote-ended, reset and declared-length-overrun paths was also handled as a stream error, leaving the connection alive despite unaccounted DATA. This could affect otherwise unrelated streams after one malformed request.

**Requirement.** [RFC 9113 §6.9](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.9) requires every flow-controlled frame to be counted against connection credit even if it is in error, unless the receiver treats it as a connection error. [§6.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.1) includes the Pad Length field and padding in the flow-controlled payload. Closing the connection or correctly accounting/discarding the stream-invalid bytes can satisfy the rule; a particular immediate-refund threshold is not the only mandated implementation.

**Minimum repair.** Debit connection credit first. If stream credit is insufficient, discard/refund the entire payload at connection scope and reset that stream. If connection credit itself is insufficient, use a connection error, including on the existing ended/reset-stream and content-length-overrun paths. No receive-window sizes, sender algorithms or ordinary flow-control policy are changed.

**Tests and controls.** Wire regressions reproduce the four connection-window failures and a padded stream-window failure. The latter requires both the stream reset and 8,192 returned connection bytes including padding, then reads a valid 4,096-byte POST and completes its response on another stream. The assertion observes frames and subsequent useful traffic, rather than inspecting a counter that merely mirrors the implementation. [nghttp2's receive accounting](https://github.com/nghttp2/nghttp2/blob/526ff38e0249acbcc4d0e8958c12cdeae9960cfe/lib/nghttp2_session.c#L7076) independently debits connection before stream credit; its [window-error handling](https://github.com/nghttp2/nghttp2/blob/526ff38e0249acbcc4d0e8958c12cdeae9960cfe/lib/nghttp2_session.c#L5495) distinguishes the corresponding scopes.

### R4. Supported HTTP/2 PRIORITY_UPDATE accepted forbidden idle targets and could reset an idle stream

**Observed behavior.** With the RFC 9218 scheduler selected, an idle push target and another prioritized idle request after exhausting the advertised concurrent-request allowance were silently accepted. Rejecting an unparsable priority dictionary could send RST_STREAM for an idle request stream, producing another invalid frame.

**Requirement.** [RFC 9218 §7.1](https://www.rfc-editor.org/rfc/rfc9218.html#section-7.1) explicitly requires a connection error for an idle push target or exceeding the active-plus-prioritized-idle request-stream allowance. [§7](https://www.rfc-editor.org/rfc/rfc9218.html#section-7) permits a connection error for an unparsable dictionary. [RFC 9113 §5.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1) forbids RST_STREAM on an idle stream. Ignoring malformed priority would be another permitted policy; selecting rejection must not itself emit an invalid idle reset.

**Minimum repair.** Add the idle-target/concurrency guards and use the permitted connection-error policy for malformed dictionaries. The existing scheduler retains only the newest idle update, so its idle contribution is at most one; no growing idle-stream map or new scheduler is added. Other schedulers retain their existing unsupported-extension ignore path.

**Tests and controls.** Seven wire cases isolate the three faults and retain legal odd idle requests, active/closed requests and unknown/out-of-range structured parameters. Positive cases synchronize with PING ACK and complete another request. The test explicitly selects the supported scheduler; an earlier probe of the unsupported scheduler's ignore behavior is not a conformance failure. [nghttp2](https://github.com/nghttp2/nghttp2/blob/526ff38e0249acbcc4d0e8958c12cdeae9960cfe/lib/nghttp2_session.c#L5291) independently rejects idle push and excessive idle-plus-active requests, while choosing to ignore unparsable dictionaries and retaining a different amount of idle state.

### R5. HTTP/3 could serialize handler-supplied malformed fields and malformed empty trailers

**Observed behavior.** Outgoing response headers did not consistently validate handler-provided field names/values. A handler could therefore cause request-only pseudo-fields, names containing invalid characters or control-bearing values to enter the response field section. Validation after Unicode lowercasing would also be insufficient because it can transform a non-ASCII key into apparently valid ASCII. Trailer values had a corresponding gap. When filtering left no encoded trailer fields, the writer could produce a HEADERS frame with a zero-byte QPACK payload, which is not a valid empty QPACK field section.

**Requirement.** [RFC 9110 §2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-2.2) prohibits generating protocol elements that do not match the applicable ABNF; [§§5.1 and 5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.1) define field-name and field-value validity. [RFC 9114 §4.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.2) requires minimum field validation and prohibits request-only pseudo-fields in responses. [RFC 9204 §4.5.1](https://www.rfc-editor.org/rfc/rfc9204.html#section-4.5.1) specifies the encoded field-section prefix; writing no prefix bytes is not a valid empty section.

**Minimum repair.** Validate the original response field name before lowercasing. Trim only edge SP/HTAB and validate each field value; omit invalid individual values while preserving valid siblings. Apply value validation to trailers and emit no trailer frame when no field remains. Existing hop-by-hop/CONNECT filtering continues to apply. The serializer does not mutate the handler's map merely to omit an invalid field.

**Tests and controls.** Unit and real local-QUIC server tests cover injected `:path`/`:status`, empty/space/colon/non-ASCII names, CR/LF/NUL/DEL values, mixed valid/invalid values and all-invalid trailers. Valid empty values, internal HTAB, opaque obs-text, ordinary bodies and valid trailers remain supported. These controls matter: replacing the defect with an unnecessarily ASCII-only value policy would break permitted HTTP fields. The approach also matches the existing HTTP/2 sender's filtering policy.

### R6. HTTP/3 could send forbidden Content-Length or invent unsupported response metadata

**Observed behavior.** The response serializer could forward configured Content-Length on informational or 204 responses. Server finalization could automatically add `Content-Length: 0` for statuses with no body, including 204 and 304, even though the number of emitted bytes does not establish the selected representation's size for a 304.

**Requirement.** [RFC 9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6) explicitly prohibits Content-Length on any 1xx or 204 response. An explicit length on HEAD/304 is permitted only with the specified representation-metadata meaning. These rules differ from successful generic CONNECT's existing framing suppression and from Capsule-specific response restrictions.

**Minimum repair.** Suppress Content-Length serialization for informational/204 responses, preserving the handler's map so a subsequent final response can reuse a valid length. Avoid automatic length synthesis where the status has no response body. Preserve explicit HEAD/304 metadata, normal HEAD written-byte counting, ordinary empty 200 length and implicit status-zero-to-200 behavior.

**Tests and controls.** Field-level tests verify 100/103, 204, normal 200 and explicit 304. Real server cases verify automatic/configured 204, automatic/configured 304, empty 200 and explicit/written HEAD metadata. Legal informational responses followed by final 200 remain valid; this server change must not be justified by clients that incorrectly reject legal 100/103.

### R7. Unsupported protocol-switch responses could be emitted on HTTP/2 and HTTP/3

**Observed behavior and requirement.** Both outgoing writers accepted `WriteHeader(101)` and could send it as an informational response on multiplexed HTTP. [RFC 9114 §4.5](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.5) and [RFC 9113 §8.6](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.6) explicitly exclude the 101 switching status. [RFC 9110 §15.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.2.2) requires Upgrade signaling for a 101 response, while the multiplexed protocols prohibit generating that connection-specific field. Omitting Upgrade or adding it therefore cannot make the serialized 101 conforming.

**Minimum repair and controls.** Both status validators now reject 101 through their existing invalid-status panic contract; existing handler recovery terminates the affected stream. Direct and wire tests require that no 101 bytes reach the peer, ordinary 100/103 followed by final 200 remain supported and another request on the connection succeeds. The HTTP/1.1 CONNECT-IP Upgrade path retains its required 101. The inspected upstream x/net writer shares the previous serializer gap; inheritance is not proof that the status is legal.

### R8. HTTP/3 response status parsing accepted non-three-digit values

**Observed behavior.** `updateResponseFromHeaders` used `strconv.Atoi` without enforcing the HTTP status grammar. It could accept values such as `20`, `+200`, `0200` or `2000`. This decoder serves the fork's HTTP/3 client API, which is used by Caddy's optional HTTP/3 reverse-proxy transport. The issue is in the server repository's transport dependency, not an edit to the protected VPN client.

**Requirement.** [RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15) defines a three-digit status code, and [RFC 9114 §4.3.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.3.2) carries that code in the response `:status` field. Malformed response handling follows §4.1.2. The separate HTTP/3 101 restriction also applies to this receive path.

**Minimum repair and controls.** Retain the existing numeric conversion and reject non-three-byte, sub-100 and 101 values. Signed, short, long, nondigit, spaced and non-ASCII variants are tested. Legal informational/final/extension codes such as 100, 103, 200, 299, 304, 471 and 599 remain usable; wire tests verify a malformed response does not prevent a subsequent extension-status response. The inherited three-digit 600–999 receive policy is preserved and tested as a compatibility boundary, not declared valid sender output: RFC 9110 calls those codes invalid and says a client SHOULD process them as 5xx. Changing that recommendation-level receiver policy was not necessary to repair the confirmed syntax/101 defects. No general response-status policy rewrite is part of this fix.

### R9. Static-only QPACK misinterpreted the field-section Base

**Observed behavior.** The QPACK dependency ignored the Delta Base sign bit and required the decoded delta to be zero. With Required Insert Count zero, it could therefore accept an invalid negative Base but reject a legal positive Base even when all fields used only the static table. This affected initial request fields, response fields and trailers through three production decoder call sites.

**Requirement.** [RFC 9204 §4.5.1.2](https://www.rfc-editor.org/rfc/rfc9204.html#section-4.5.1.2) defines `Base = Required Insert Count + Delta Base` for sign zero and `Base = Required Insert Count - Delta Base - 1` for sign one. A decoder MUST reject the sign-one form when Required Insert Count is less than or equal to Delta Base. Conversely, a section without dynamic references may use any valid nonnegative Base. Static-only operation is not permission to discard the sign or require Base zero. [§4.1.1](https://www.rfc-editor.org/rfc/rfc9204.html#section-4.1.1) requires support for integers through 62 bits and permits limits on excessively long encodings.

**Minimum repair.** A local `decodeFieldSection` wrapper validates the relevant prefix, rejects a negative Base and accepts/normalizes a legal positive Base before invoking the unchanged static-only decoder. It does not modify received bytes, enable dynamic compression, increase the advertised table capacity or replace/upgrade the dependency. The three initial-request/response/trailer call sites use the wrapper. Existing nonzero Required Insert Count and dynamic-reference rejection remains intact.

**Tests and controls.** Fifteen unit prefix cases cover zero/positive/maximum-62-bit Base, bounded nonminimal encodings, truncation, range/length overflow, negative Base, nonzero Required Insert Count and dynamic references. Twenty-eight real-QUIC cases exercise request/response initial fields and trailers with zero, positive, prefixed, nonminimal, maximum and negative forms. On baseline, twenty cases fail and eight controls pass; focused repaired race tests pass on both supported Go toolchains. Invalid prefixes retain the existing connection-level QPACK decompression-error action. For integer implementation limits, RFC 9204 §7.4 describes a request-stream error and RFC 9114 §8 permits escalation; the tests encode the selected connection error, not a universal scope requirement for every limit. These focused results do not substitute for the final full transport/client matrix.

**Independent checks.** [nghttp3's signed Base calculation](https://github.com/ngtcp2/nghttp3/blob/d29ceea176cebc1f41c9d818c3b1825143d3f813/lib/nghttp3_qpack.c#L3387) corroborates both negative rejection and positive addition. [ls-qpack's static-section handling](https://github.com/litespeedtech/ls-qpack/blob/91567706c41c0d97ab8dc576873ecd472d7869fa/lsqpack.c#L3998) corroborates that static fields do not depend on positive Base, but also ignores the sign in that branch. That comparator limitation does not waive the explicit negative-Base MUST and was not copied.

### R10. QUIC explicit zero idle timeout was changed into a finite timeout; large values could overflow

**Observed behavior.** Decoding `max_idle_timeout` applied a positive floor before preserving its zero semantics. An explicitly advertised zero therefore contributed an invented five-second timeout, while omission contributed zero. The same calculation multiplied a full QUIC varint into signed nanoseconds before checking whether the result could fit, allowing wraparound to negative or unexpectedly short values.

**Requirement.** [RFC 9000 §18.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-18.2) defines integer milliseconds and says zero/omission disables that endpoint's advertised idle timeout. [RFC 9000 §10.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-10.1) uses the only nonzero value when the other endpoint advertises zero, with the transport's PTO rule. A parser must not turn a valid large integer into a small or negative timeout through conversion overflow.

**Minimum repair.** Preserve explicit zero, bound large nonzero values before multiplication and saturate values outside `time.Duration`'s representation. Preserve the inherited positive-value policy. The current higher-level API normally supplies a nonzero local timeout; these tests do not claim that every finite remote value is represented exactly or that both-zero disables all API timers.

**Tests and controls.** Parameter tests cover explicit zero, ordinary positive values, the largest exact millisecond duration, the first overflowing value, positive wraparound and the maximum QUIC varint. Connection tests decode actual parameter bytes and verify the resulting effective timeout: omission/zero leave the local nonzero timeout, a smaller ordinary remote value wins and large/overflowing values do not shorten it. A TLS-handshake test verifies that the peer's explicit zero survives real transport-parameter exchange. Independent zero handling is corroborated by [quiche](https://github.com/cloudflare/quiche/blob/12d2af7dd19046eebfa8c14b409a31a0c38fbe48/quiche/src/lib.rs#L7857) and [ngtcp2](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L13220).

### R11. Locally generated ICMPv6 errors could answer Redirect

**Observed behavior.** `mayICMPv6Error` allowed all informational ICMPv6 types at or above 128. Redirect is informational type 137 but is an explicit exception, so both Destination Unreachable and Packet Too Big could be generated in response to it. The issue was reproduced directly, after an IPv6 extension header, and through both actual session input-reader paths with a fake host device.

**Requirement.** [RFC 4443 §2.4(e.2)](https://www.rfc-editor.org/rfc/rfc4443.html#section-2.4) prohibits originating an ICMPv6 error as a result of receiving an ICMPv6 Redirect. This is independent of the multicast-destination exception for Packet Too Big in item (e.3); the exception does not override the Redirect prohibition.

**Minimum repair.** Add the explicit type-137 exclusion to the existing predicate in `internal/ip/ip.go`. Preserve parsing, checksums, address rules and rate limiting. [FreeBSD's `icmp6_error`](https://github.com/freebsd/freebsd-src/blob/16a79708d089423ec0c3d32f25e7ca97ae58e97b/sys/netinet6/icmp6.c#L341) applies the same explicit Redirect exclusion. The inspected [Linux v6.12 helper](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/ipv6/icmp.c) has different high-bit handling; one helper does not prove every complete Linux input path behaves the same way, and cannot waive the RFC's explicit prohibition.

**Tests and controls.** Cover direct/extension-header Redirect, ordinary ICMPv6 errors, Echo Request/Reply, unsuitable sources, fragments and Packet Too Big's multicast case. Session tests first confirm normal feedback for blocked Echo, then process Redirect and forward a subsequent normal UDP packet through the same reader. This synchronization proves the negative was observed after the relevant input was processed. The fixture is not a valid native Neighbor Discovery announcement and does not claim a kernel capture; receiving it still cannot justify the forbidden secondary error.

### R12. Validation of a new QUIC address bypassed its amplification allowance

**Observed behavior.** Initial handshake accounting did not cover the separate server migration-probe path. A real encrypted 1-RTT packet relayed through a fresh NAT source caused an unconditional 1,200-byte reply, while the global packet handler already considered the original handshake address validated. With PMTU discovery disabled to isolate a small packet, the observed new-path input was 26 UDP bytes, the permitted three-times allowance was 78 bytes, and the first server output was 1,200 bytes. An earlier exploratory input was a 1,409-byte PMTU probe; its 1,200-byte reply was within allowance and correctly passed. That exploratory control is not presented as a failing amplification case.

**Requirement.** [RFC 9000 §9.3.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.3.1) applies the address-validation amplification limit to a new peer address. Authentication proves possession of connection keys, not ownership of an arbitrary source address. [§§8.2.1 and 8.2.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.2.1) require 1,200-byte challenge/response padding unless it exceeds the anti-amplification allowance. A small allowed challenge can validate address ownership but does not prove the path's minimum MTU; a subsequent expanded challenge is required.

**Targeted repair.** The existing bounded candidate-path records retain received/sent byte totals and supply the remaining permitted packet size to the probe packer. The 26-byte UDP case now receives 78 bytes instead of 1,200. Paths do not borrow another candidate's credit. A normal full-credit path still gets a 1,200-byte probe. The manager distinguishes address validation from successful expanded-probe validation, uses a new unpredictable nonce for the follow-up and prevents an old duplicate response from completing that second check.

**Cross-path response control.** RFC 9000 §8.2.3 explicitly allows a matching response to arrive on another network path. The stored candidate address and local packet metadata therefore dispatch the second MTU challenge on the originally challenged route even when the response arrives on the old path, without waiting for new input on the candidate. No incorrect same-path receipt restriction is added. [ngtcp2's probe writer](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L4766) independently clamps output to the path allowance and records undersized probes; [its allowance calculation](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L2625) is three times received minus sent bytes.

**Tests and controls.** `TestNATRebindingAmplificationLimit` measures actual UDP output. `TestNATRebindingCrossPathResponse` runs small and large client DATAGRAM cases, forwards exactly one initial new-path packet, routes validation responses over the old path, observes the required second full-size challenge on the new route and verifies application datagrams in both directions after migration. Unit controls retain separate budgets, small/full probes, duplicate-nonce rejection, stored local-source metadata and ordinary PING behavior. These are local real TLS/QUIC/UDP and controlled-state tests, not every Internet NAT or native Apple path.

### R13. QUIC path challenges were omitted, incompletely echoed or sent on the wrong route

**Observed behavior.** A server early return for its already active address skipped challenge handling, so valid revalidation of the active path timed out. Parsing retained only the last PATH_CHALLENGE in a packet. Ordinary short-header output did not consistently apply the required path-control padding. Separately, apparent migration did not send the required challenge to the previously active path. Merely placing new responses in the general active-path queue would also be insufficient: another packet in the same receive batch could promote a new path before the queued response was transmitted.

**Requirement.** [RFC 9000 §8.2.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.2.2) requires an echo for each received challenge on the route where it was received, with the padding/amplification qualification. The sender SHOULD NOT combine multiple challenges, but that recommendation does not remove the receiver's echo obligation. [§9.3.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.3.3) separately requires validation of the previously active path on apparent migration. A response received on another path remains acceptable; an ACK alone is not path validation.

**Targeted repair.** Retain all challenges from the packet, split responses into bounded packets and preserve path-control padding when permitted. A server-only queue captures the remote address, local packet metadata and CID at receipt, so congestion deferral or a later receive-batch migration cannot redirect a response. A fresh previous-path challenge is initiated once per tracked candidate, with bounded recent unpredictable tokens and captured old-route metadata. Another candidate or an expired/recreated candidate can initiate another attempt; this is not a once-ever flag for the old address. Migration does not depend on the old path still working.

**Congestion and lifecycle controls.** Active-path controls consume ordinary congestion credit. Former-route controls use independent probe history so their ACK/loss does not alter the new route's RTT/window, as required by §9.4. A persistent bounded route-credit record limits outstanding probe traffic and survives removal of the last unsent queue entry. Idempotent shared handlers on every frame release credit safely on ACK/loss; a multi-response loss cannot invoke a nil handler or free a later packet's credit. The existing 256-response resource bound is retained, with at most three additional old-path challenge slots. This is not a claim of unlimited overload tolerance.

**Tests and controls.** Actual UDP fixtures reproduce active-path timeout and missing old-path challenge on the exact baseline. Repaired fixtures observe all responses to two challenges in one authenticated packet, subsequent application data, and old-path probes with both viable and deliberately dead return paths. Small-credit splitting also exercises 130 challenges across two response packets. Controlled tests defer output through migration, preserve original local-source/interface metadata, re-use rather than recreate outstanding credit, drive the actual loss detector for a multi-frame packet and check bounded storage and duplicate callbacks. Any-path matching is preserved, including old-path validation responses returned through the new relay socket.

### R14. Migration selection and the reserved sending CID could diverge

**Observed behavior.** The sequence B/non-probing/10, A/non-probing/11, B/PATH_RESPONSE/12 could promote B because the code compared against the largest packet number of any kind and retained historical non-probing state. A carried the highest non-probing packet, so a newer probe could not justify selecting B. When migration did select a candidate, the ordinary sender also kept the old active destination CID instead of promoting that path's reserved validation CID, leaving the reservation stranded.

**Requirement.** [RFC 9000 §9.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.3) associates migration with the path of the highest-numbered non-probing packet. [§9.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.5) constrains CID reuse across destination addresses and explicitly permits an exception for some NAT changes with unchanged incoming DCID. The strict no-reuse finding concerns intentional changed-DCID migration where that exception does not apply; choosing the reserved fresh CID for ordinary NAT rebinding is permitted, not uniquely required.

**Targeted repair.** Track the highest non-probing packet/address separately. Validation completion cannot override a newer non-probing packet on another path. Transfer the selected path's reserved CID and already-registered reset token into the ordinary sender, then clear its probing reservation. Support older still-live reservations after automatic active rotation without treating them as retired solely because of a local sequence watermark. Recognize live duplicates before historical shortcuts so a reserved CID cannot re-enter the unused pool and be assigned to another path. Peer Retire Prior To remains distinct from that local watermark and is processed even when a NEW_CONNECTION_ID frame is reordered.

**Queued CID lifetime.** Each bound control frame pins its captured CID until physical transmission or cleanup. Local rotation/promotion defers retirement and reset-token removal until these references drain; mandatory peer retirement overrides pins. A former route then requires a legal unused replacement, shared across its queued batch, and waits if none is available. An active route waits for a legal active replacement. Negotiated zero-length CIDs remain a valid separate control; CID exhaustion is not represented as zero-length negotiation. The final exhausted-current-control and negotiated-zero-length tests are supporting compatibility controls, not additional demonstrated defects: both passed on the repaired CID state before the send-queue snapshot change. That result does not claim that the new helpers existed or these tests ran unchanged on merged main.

**Tests and independent check.** The migration handler regression reproduces the wrong path selection and missing CID promotion with controlled unpacking; same-DCID NAT, changed-DCID migration and a newer original-path non-probing packet remain distinct. CID tests cover older reservation promotion, duplicate/conflicting reserved frames, local versus mandatory retirement, shared replacement, deferred sends, reset-token cleanup and active-CID limits. [ngtcp2's migration handling](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L8289) applies the §9.5 distinction, and [its validation completion](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L5683) promotes the bound CID. It corroborates the required outcome, not this implementation's exact queue/refcount architecture.

### R15. The asynchronous QUIC sender could redirect an already packed packet after migration

**Observed behavior.** Ordinary packets were packed for the then-current destination CID/route, but the send worker loaded the current remote address only when draining the queue. A migration between enqueue and drain could send the old packet to the new destination, including with inappropriate local-source ancillary data. The baseline deterministic regression fails for both ordinary and GSO output: the first old-route packet is written to the new address.

**Requirement and repair.** RFC 9000 §§9.4–9.5 require path/congestion and sending-CID consistency. On deliberate changed-CID migration, redirecting an old-CID packet to the new destination can also violate §9.5; its unchanged-DCID NAT exception must not be generalized to every migration. Queue entries now snapshot the immutable remote address/local packet metadata record at enqueue and use that record during actual write. Newly queued packets capture the new record. Packet content, ECN and GSO settings remain those selected for each entry.

**Controls and evidence.** `send-queue-route-before.log` records both baseline failures; the repaired `TestSendQueueRetainsQueuedPacketPath` delays the worker until after a route switch and checks old/new address, local metadata, payload, GSO and ECN independently. This uses the production queue and deterministic raw-socket double, not a live UDP capture. Existing queue blocking/error and CID/migration tests supplement it; real UDP migration is covered separately above.

### R16. Buffered QUIC packets could earn amplification credit again on an internal decryption retry

**Observed behavior.** `handleOnePacket` credited received bytes unconditionally, but the run loop also calls it when retrying already received undecryptable packets. Coalesced protected packets clone metadata before queuing, so retrying them inflated both received statistics and pre-validation allowance. In the actual handler/budget regression, one 23-byte input became 46 accounted bytes and an allowance of 138 instead of 69; a 46-byte coalesced input became 92 accounted bytes and 276 instead of 138.

**Requirement.** [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1) bases allowance on received network bytes. An internal key/decryption retry is not another UDP receipt. A separately received duplicate datagram is real network input and may legitimately add credit. This defect does not require enabling application 0-RTT: a key-availability event retries queued levels while another opener may remain unavailable. The Caddy app's `Allow0RTT=false` remains unchanged.

**Minimum repair and controls.** An internal `bytesAccounted` bit credits physical receipt once and is preserved by coalesced-packet clones/deferred processing. New network packet objects begin uncredited and earn their normal allowance. Tests isolate parsing/queuing/retries with controlled decryption and the real unvalidated sent-packet handler, cover still-unavailable and subsequently available keys, and retain a separately received duplicate control that already passed baseline. No packet-number deduplication, frame validation, TLS or cryptography changes. These are measured budget/handler failures, not a claim of a captured live oversized response or real 0-RTT TLS decryption. [ngtcp2's receipt wrappers](https://github.com/ngtcp2/ngtcp2/blob/697d5530238525a7d560e0bc2ea01efe4fe17581/lib/ngtcp2_conn.c#L6546) credit the compound network datagram; its buffered protected-packet processing does not repeat that network receipt accounting.

## Minimum necessary scope of the transport changes

Most HTTP field, status, idle-timeout and ICMP changes are local guards or error propagation. The migration repair is materially larger: a three-times limit cannot be fixed safely by simply suppressing every full-size probe, because an undersized success requires a follow-up MTU probe; responses must retain their route across congestion and receive-batch migration; selected CIDs must move with the route; and queued CID references must survive local retirement while obeying mandatory peer retirement. The send worker and receipt retry boundaries also needed separate reproductions and corrections. Omitting those coupled cases would leave either an explicit requirement unmet or a regression in ordinary migration.

New state remains limited to bounded candidate accounting, recent old-path tokens, bound control queues/credit, CID references and route/receipt metadata. The repair reuses existing packing, ACK/loss, congestion and send paths. It does not add a general multipath scheduler, new cryptography, client dialect or unrestricted buffering. Independent source review challenged intermediate designs, including route changes before deferred send and credit that disappeared when a queue entry was removed; those intermediate designs were corrected. The larger state-machine surface is an explicit regression risk requiring full package/race, actual UDP migration and unchanged-client validation, not described as a collection of unrelated one-line fixes.

The frozen implementation changes **17 production Go files, with 886 added and 126 removed lines**. Nine of those files, with 737 added and 87 removed lines, cover the coupled QUIC path/CID/receipt/queue work. The remainder is one IP file, one HTTP/2 file, five HTTP/3 files and the QUIC parameter parser. Added regression tests and exact fork reproduction records are separate from these runtime counts; the full change-footprint ledger accompanies the evidence. This is materially larger than the previous six-file reassessment and is reported that way. Source changes were frozen before the root's final full validation; only the completed source-bound ledger below can establish those final results.
