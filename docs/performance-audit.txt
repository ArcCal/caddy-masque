PERFORMANCE FACTORS AND EXPERIMENTS
1. Capsule encoding (tunnel.go writeCapsule): proto.Append(nil,c) allocates a new
   frame for each packet, before taking the writer mutex. Every H2 packet also
   calls Flush. CPU/GC and syscall/frame overhead can limit small-packet rates.
   Experimental auditReuseWriter uses a bounded, writer-owned buffer under the
   existing mutex. Wire bytes are compared across 0/64/1280/65535 byte payloads.
   It deliberately changes no framing, flush frequency, ordering, or security
   behavior. Buffer retention trades bounded per-session memory for allocation
   savings. Candidate stays in a Go overlay, not production.
2. Capsule decode (internal/proto/capsule.go): Push appends, Next copies payload,
   and the empty buffer is nilled. This ensures independently owned values and
   bounds retention, but creates steady allocation on stream transports.
   Ownership-preserving reuse needs separate lifetime tests; no unsafe zero-copy
   patch is proposed. Production decoder allocations are benchmarked.
3. Historical lease admission (core.acquire): each fresh assigned address scans
   every remembered user under poolMu and clones unrelated address slices. The
   recent map retains historical entries indefinitely unless that name reconnects.
   This is admission latency, not packet throughput. Candidate adds a membership
   check before cloning/updating unrelated entries, preserving invalidation for
   an actually reused address. Adopted after the overlay experiment. Benchmarks
   use 0/1000/10000 historical names, which
   can accumulate across configured-user churn; they are not a claim that all
   deployments have that history. This does not remove the O(history) scan or
   claim to solve map retention. It only eliminates copies of unrelated slices.
4. Pool near exhaustion: production allocator scans sequentially under poolMu.
   /112 is an accepted IPv6 pool. With just one free entry it measured about
   2.27-2.38ms vs 4.59-5.82us for a similarly full /24, and 138-159ns for a fresh
   /64. This is a worst-case accepted configuration, not typical /64 behavior.
   Do not remove conntrack cleanup or address ownership checks to speed admission.
5. Host-to-client queue: 1024 packets, age cap 200ms. A full queue allocates/copies
   the packet before dropping it. A slow transport can therefore cause avoidable
   GC work. Increasing queues trades loss for latency/memory and is not a general
   fix. Full-queue drops currently bypass the exported drop counter, while age
   drops increment it; the metric cannot fully diagnose saturation from code.
6. One TUN reader and a userspace copy per accepted host packet; every inbound
   client packet calls one TUN write. No TUN multiqueue/GSO batching is configured.
   These are scalability candidates, not measured kernel bottlenecks here.
   Kernel impairment/netns end-to-end capability must be checked separately.
7. Transport tradeoffs: H1/H2 carry IP packets on reliable TCP streams; loss can
   impose outer TCP head-of-line delay and interact with inner TCP. H3 Capsules
   still serialize reliable stream bytes. H3 DATAGRAM avoids that reliability but
   still shares congestion control and bounded queues. Never silently fall back
   to reliable delivery for an oversized negotiated Datagram (RFC 9484 10.1).
8. QUIC flow control defaults: 512KiB initial stream window, 768KiB initial
   connection window, 6MiB stream maximum and 15MiB connection maximum. These can
   constrain a high-bandwidth/high-RTT Capsule stream, while DATAGRAM frames are
   not stream-flow-controlled. An increase needs memory-budget and peer-window
   measurements; no unconditional window inflation is justified. The bandwidth-
   delay product is throughput times RTT: windows should be compared with that
   measured demand and concurrent-connection memory budget, not raised blindly.
9. QUIC Datagram queues: 32 outbound frames (Add waits), 128 inbound frames
   (overflow drops). The receiving fork allocates before checking full. The
   server also has its own 1024-packet queue. Queue depth alone does not imply a
   WAN throughput ceiling; pacing, congestion, RTT, loss and scheduling matter.
10. MTU: server default is 1350, with IPv6 minimum 1280; initial QUIC packet sizing, actual
    DATAGRAM overhead and PMTU determine usable payload. IPv4 DF feedback, IPv4
    fragmentation and IPv6 MTU probes are protocol/security obligations. Disabling
    them or increasing MTU without path validation is a rejected optimization.
11. Authentication: Argon2 resource cost and per-source/global admission bounds
    intentionally prevent brute-force and memory/CPU exhaustion. Cached successful
    credentials accelerate reconnects. Concurrency follows runtime.NumCPU rather
    than CPU/memory cgroup budget; deployment tuning is warranted, not weaker hashes.
12. QUIC uses paced Reno mode (NewSentPacketHandler passes true to the
    cubicSender constructor), inherited initial 32-datagram congestion window
    and maximum 10000 datagrams. This is distinct from stream flow control.
    Congestion algorithms/initial-window choices need fairness, loss and path
    tests before tuning; no alternative controller is adopted. UDP socket
    buffers target 7MiB; actual kernel limits and scheduling can change drops.
    QUIC UDP batching/GSO support must not be confused with the unbatched TUN
    path. No disabled security, congestion-credit or anti-amplification check is
    an acceptable speed optimization.
13. Shared-map lock contention, session-limit scans, metrics collection, scoped
    DNS resolution (5s bound), conntrack subprocess cleanup, TLS/QUIC handshake,
    and 30s host-network repair are additional latency/resource factors. Route
    checks already use binary search; replacing them without evidence is rejected.

SECURITY AND IETF BOUNDARIES
Preserve source-address ownership/BCP38, private/link-local isolation, route scope,
checksum validation before local ICMP, conntrack clearing before address reuse,
TLS verification, authentication strength, bounded queues and the correct stream
vs connection error codes. A throughput improvement obtained by dropping these
checks is outside the user's requirements. Default session limits, cancellation,
website behavior, reload rollback, graceful shutdown and malformed-input isolation
are covered by the existing root suite; package-level skips are tracked below.

NF TEARDOWN DIAGNOSIS (FAILURE RETAINED)
The unchanged NF helper used Backend::Drop (local conn.close) then waited only
for the TCP SOCKS listening address to become bindable. This was not a completed
QUIC wire shutdown: a scratch helper captured Quinn endpoint clones BEFORE core
cancellation, then observed open_connections()==1 after the local listener was
released. Awaiting each Endpoint::wait_idle with the existing 20-second operation
bound reduced the count to zero before printing PASS/exiting.

Quinn 0.11.12 endpoint.rs documents wait_idle as needed before process exit to
make a good-faith effort to notify peers; immediate exit can force their idle
timeout. Exact isolated original dual-stack/h3 tests passed 3+8 times (42.616s,
115.634s). A paired scratch comparison with the same three Go repetitions passed
both with drain (45.650s) and without drain (43.715s); the latter still logged
one pending QUIC connection after local-listener release. Therefore the lifecycle
gap is directly confirmed, while the original intermittent server residual was
not reproduced in isolation and its exact causal stack was not captured. Do not
claim the repeated passes alone explain or erase that failure.

Artifacts: interop-nf-diagnostic.txt, interop-nf-diagnostic-8.txt,
interop-nf-drain-candidate.txt, interop-nf-drain-disabled.txt;
